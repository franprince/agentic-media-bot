# Technical Specification: Agentic Media Bot

## Core Technologies
- **Runtime:** `bun`
- **Language:** TypeScript (`strict` true)
- **Bot Framework:** `grammy`
- **AI Integration:** `@ai-sdk/google` (`gemini-2.0-flash`) or `@ai-sdk/openai` (via `createOpenAI` bridge) for Ollama (local or cloud). Utilizes tool calling with `maxSteps: 5` for multi-step reasoning.
- **Webhooks**: Exposes endpoints via `Bun.serve` on port 3000:
    - `/plex-webhook`: Processes Plex Media Server events (Plex-specific multipart/form-data).
    - `/radarr-webhook`: Processes Radarr JSON notifications (Grab, Download).
    - `/sonarr-webhook`: Processes Sonarr JSON notifications (Grab, Download).
    - `/nzbget-webhook`: Processes NZBGet JSON payloads (event, title, speed, eta).
- **HTTP Client:** Native `fetch` API.
- **Testing:** `bun:test` for unit/integration tests, using **Mock Service Worker (MSW)** for network interception and service mocking.

## Project Structure
- `src/bot.ts`: Entry point. Initializes Telegram bot, logs incoming traffic, and handles direct commands like `/start` and `/status`.
- `src/setup.ts`: Standalone interactive CLI tool for initial configuration and dependency installation.
- `src/agent/index.ts`: LLM abstraction. Handles message history, conditional model loading, and iterative tool execution.
- `src/services/`: Modular wrappers for Radarr, Sonarr, qBittorrent, Plex, and NZBGet APIs.
- `src/services/transcription.ts`: Audio transcription abstraction. Resolves the active provider via `resolveTranscriptionUrl()` (explicit `TRANSCRIPTION_URL` > Ollama-derived > OpenAI-derived > null/Gemini). Derives the file extension from the MIME type via `mimeTypeToExtension()` to correctly label the Whisper multipart upload. Explicit URL failures hard-fail; auto-derived failures silently fall back to Gemini.
- `src/agent/tools.ts`: Unified tool repository for AI integration.
- `src/services/database.ts`: Persistence layer using `bun:sqlite` for conversation history and user personalization (names). The database is stored in `data/bot_data.sqlite` to facilitate persistence via Docker volumes.
- `src/services/webhooks.ts`: Webhook handler for external service integration (e.g., Plex).
- `src/types/`: TypeScript interfaces representing external payloads.
- `data/`: Directory for persistent data (database files, etc.). Must be mapped to a persistent volume in Docker/Coolify.

## Security & Authentication
- The bot must implement an allowlist of Telegram User IDs. If a message is received from an unknown ID, it should be ignored or gracefully rejected.
- API keys for Radarr, Sonarr, Plex, and Gemini must be injected via read-only `.env` file.
- `/restart` command authorization is enforced using `ALLOWED_USER_IDS`.
- `/restart` stops the current polling runner, launches `scripts/restart-bot.sh` as a detached supervisor (passing current PID + absolute script path), and exits the current process; the supervisor waits for shutdown, force-kills if needed, and starts a fresh process with Bun. Restart paths resolve from project root instead of current shell directory. `BOT_RESTART_COMMAND` can override this behavior. If supervisor launch fails, it retries with a detached `nohup` fallback before in-process runner fallback.
- `/restart` persists the requester chat ID and, on successful startup, sends a localized "back online" confirmation once, then clears the notification metadata.
- Slash commands are excluded from generic `message:text` LLM handling to avoid command leakage into tool-calling flow.

## AI Agent Design
- The agent utilizes an LLM capable of function calling.
- **Context Management**: Conversation history is stateless per-request but keeps a bounded history within the Telegram session. The `trimHistory` logic (in `src/services/database.ts`) prunes history to the last 20 messages to maintain model focus and avoid context "stickiness". Each save stamps `conversations.updated_at` (epoch milliseconds; the column is added to older databases at startup by `ensureConversationTimestampColumn`), read through `getConversationUpdatedAt`.
- System prompt strongly guides the agent to use tools rather than answering based on local knowledge.
- Recursive execution loop (`maxSteps: 5`) allows the agent to audit libraries across multiple sections (movies and shows).
- **Auditing Intelligence**: The bot can verify library consistency, identify missing media, and list unwatched episodes for series.
- **Proactive Notifications**: Users can subscribe to download completion alerts, which are triggered by Radarr/Sonarr/NZBGet webhooks.
- **Local Adaptation**: System prompt contains strict technical protocols to ensure reliable tool adherence on local LLMs.
- **Tool-Argument Guardrails**: Tool schemas tolerate missing IDs, but execution returns a "search first" response with suggestions to avoid invalid tool calls and crashes.
- **Radarr Search Resilience**: If Radarr lookup fails during a title-based add, return a user-facing error instead of crashing.
- **Tool Error Containment**: Radarr tool execution paths should return structured error messages for API 4xx/5xx responses rather than throw and abort the full LLM turn.
- **Defensive Tool Filtering**: Before tool execution, the agent filters out any `undefined` tool mappings in `src/agent/index.ts` to prevent AI SDK crashes (`TypeError: tool2.type`).
- **Media Deletion Tools**: `removeMovieTool` and `removeSeriesTool` use external database IDs (TMDB/TVDB) to fetch internal Radarr/Sonarr IDs. They require explicit user confirmation (via the `confirm` flag) and a choice regarding file deletion before performing the `DELETE` API call.
- **IMDb Validation & Interactive Config**: `addMovieTool` and `addSeriesTool` prioritize search-by-id when an `imdbId` is provided. They now also return available quality profiles and root folders when `confirm` is false.
- **Anime Detection**: `addSeriesTool` automatically detects Anime (via genres) and sets `seriesType: "anime"` in Sonarr POST payloads.
- **Restricted Notifications**: Plex webhook notifications are restricted to playback events (play, resume, scrobble). Library additions (`library.new`) trigger internal cache invalidation but do not send outward notifications.
- **History Migration**: Dynamically renames legacy tool calls in the conversation history to maintain compatibility with updated tool schemas.
- **Real-time Status Feed**: Captures "thinking" preamble from the LLM to provide localized, real-time status updates via the Telegram `onStep` callback.
- **Localized Entry Status**: `src/bot.ts` localizes initial "thinking" and restart catch-up status messages based on detected user-message language.
- **Final Language Enforcement**: `processUserMessage` performs a post-generation language guard; if output language does not match the detected user language (es/en), it rewrites the final text in the target language while preserving content/format. The rewrite is one more model request, so `shouldRewriteForTargetLanguage` (`src/agent/utils.ts`) skips it for an English conversation when `readsAsEnglish` (`src/agent/status.ts`) finds the reply to be English prose: at least four English-only function words and at least twice as many as Spanish-only ones, counted outside bold and quoted titles, with no `¿` or `¡`. With too little prose to judge, or in a Spanish conversation, the signal detector decides as before.
- **Deterministic Count Prefix**: Final responses prepend a localized exact-count line for Plex country/genre tool results using `totalFound`.
- **Count Source of Truth**: Exact-count prefixes must use tool results from the execution pass (`firstPass`) even when a synthesis model generates the final prose.
- **Plex Tag-Key Normalization**: Country/genre filters parse Plex tag keys that may arrive as full query paths (not only numeric IDs), ensuring accurate filter requests.
- **Plex Direct Tag-Path Preference**: When Plex provides a full filter path in tag keys, the service uses that path directly to preserve server-side filter semantics.
- **Deterministic Plex Browse Rendering**: Final text for Plex country/genre browse requests (`searchPlexByCountry` / `searchPlexByGenre`) is generated from tool payload (`totalFound` + `sampleItems`) rather than relying only on LLM prose.
- **Deterministic List Label**: Plex country/genre search tools return `queryType` + `searchParam` + `listLabel` so output uses "This is the list of {genre} media:" for genres and "This is the list of media from {country}:" for countries.
- **Country Noun Normalization**: Status rendering and prompt rules normalize country demonyms to country nouns to keep tool intent explicit and logs consistent.
- **Tool-Boundary Country Canonicalization**: `searchPlexByCountry` normalizes demonyms to country nouns in the tool schema before execution.
- **Single Country Canonicalizer**: Country normalization for tool execution, status rendering, and tool-call logging is centralized in `src/services/plex.ts` to avoid drift.
- **Accent-Resilient I18N Detection**: Status language detection handles common Spanish forms with and without diacritics. `countSpanishSignals` matches most listed words anywhere in the text so inflected forms count ("buscame", "obtengo"), but the words that occur inside English ones match only at the end of a word (`esta`, `esto`, `este`, `pero`: "respuesta" yes, "timestamps" no) or at the start of one (`hola`, `cola`, forms of *estar*: "colas" yes, "Nicolas" no). A few words count twice (`tengo`, `esta`, `esto`, forms of *estar*) so that a longer message with only one of them still reads as Spanish.
- **Plex Result Deduplication**: Country/genre aggregation across multiple movie and show sections deduplicates media entries before computing `totalFound`.
    - **Strict Country Tag Filter**: After Plex country browsing, each item is verified by fetching metadata and checking `Country` tags against the requested country; language tags are ignored and co-productions are included by default (`primaryOnly: false`).
    - **Media Type Labeling**: Search results and browse samples are enriched with a `mediaType` label based on the service and item type.
- **Title-Level Country Verification**: `searchPlexByTitleOnly` includes normalized `countries` and `primaryCountry` so country yes/no answers are grounded in Plex metadata.
- **Ranked Country Query Support**: `searchPlexByCountry` supports `ranked` and `limit` arguments and orders results by available Plex rating fields for top-N responses.
- ** deterministic Original-Title Rendering**: `buildPlexBrowseAuthoritativeText` and webhook notifications append `originalTitle` when different from displayed title.
- **Browse Title Enrichment**: Ranked country sample items fetch Plex item metadata and fallback to `titleSort` when `originalTitle` is unavailable.
- **Cross-Service Alias Recovery**: When foreign-script titles still lack Latin aliases after Plex metadata enrichment (in browse results or webhook notifications), the bot performs best-effort Radarr/Sonarr lookup (title/year) to recover English aliases.
- **Alias Fallback Rendering**: If `originalTitle` is missing, deterministic rendering can use enriched `aliasTitle`; if a non-Latin title still has no alias, output explicitly marks the English/Spanish alias as unavailable.
- **Intent-Based Tool Gating**: For detail/info/synopsis user intent, add tools (`addMovie`, `addSeries`) are removed from the tool set unless explicit add intent is detected.
- **Interactive Buttons Layer**: The agent logic includes a post-processing regex layer to extract `BUTTON: Label | callback_data` patterns from LLM responses, populating the Telegram `InlineKeyboard`. `selectReplyButtons` (`src/agent/response.ts`) decides which buttons are shown: buttons returned by a tool (add/remove confirmations, e.g. data `add movie <tmdbId> <defaultProfileId>`, label naming the default profile) are authoritative and the model's `BUTTON:` lines are dropped; otherwise the model's buttons are used, without notification buttons while a confirmation is pending. Buttons are de-duplicated by data and callback data is cut to Telegram's 64-byte limit (longer data fails the whole message). `detectConversationLanguage` treats button payloads (`add movie …`, `Remove the movie …`, snake_case data) as language-neutral, so a tap keeps the conversation's language, and recognises colloquial Spanish commands ("bajame", "borrá", "parte", matched as whole words).
- **Error Diagnostics**: The `/audit` command provides a deep-dive into `/tmp/agentic-media-bot-restart.log` to identify root causes of crashes.
- **Step 0 — Tool Routing (token budget)**: Before Step 1's tool-calling loop, `selectToolGroups` (`src/agent/toolRouter.ts`) picks which of nine tool groups (`movies`, `series`, `library`, `discovery`, `downloads`, `system`, `watchlist`, `reports`, `ersatztv`) a message needs, and Step 1 receives only those tools plus the matching system-prompt sections (`buildSystemPromptTemplate` in `src/agent/prompts.ts`). Evidence, cheapest first: (1) Spanish/English keywords, no model call; (2) conversation context — a short reply ("4", "sí", a button callback) inherits the groups of the tools used in the previous turn; (3) a ~300-token classifier request to the fast model when 1 and 2 find nothing; (4) the full tool set if all of that fails. Greetings and capability questions get no tools. A question about finished downloads ("what did we download last?", "qué bajamos ayer") gets `library` as well as `downloads`, because the queue tools only show what is still downloading. It never gates execution: a narrowed model that lacks a tool answers `NEED_MORE_TOOLS` and is re-run once with a wider set. Once every tool is offered the prompt replaces the marker rule with an `UNSUPPORTED` rule (say plainly that the request is not covered), so there is nothing left to ask for; a reply that is still only the marker becomes the localised `noToolReply` (es/en, `src/agent/response.ts`). The marker is never sent as a status update and is removed from the assistant messages before they are saved and before the synthesis pass reads them (`scrubMarkerFromMessages`), so no model reads it back. The loop still widens only once: after a partial widening a second marker ends in `noToolReply` without every tool having been offered. The conversation sent to the model is a budgeted *view* of the stored history (`src/agent/historyBudget.ts`): older tool results are compacted to IDs/titles/counts, oldest turns are dropped first (`AI_HISTORY_CHAR_BUDGET`, default 4000 chars), and the view always starts at a user message; the stored history is unchanged. All chat models are built in `src/agent/provider.ts`, which reads `OLLAMA_API_KEY` for hosted OpenAI-compatible endpoints and waits out HTTP 429 (`Retry-After`) per request so tools from earlier steps never run twice. Measured on Groq (`openai/gpt-oss-120b`): a request went from ~10,100 prompt tokens (always) to ~700 (small talk), ~900–3,100 (routed) and ~5,100 (full fallback) before history. The earlier Ollama-native classifier (`narrowToolsForMessage` in `src/agent/intentRouter.ts`, `mediaTools.classifyIntent`) is no longer called by the agent loop; it only covered two domains and needs a native Ollama `/api/generate` endpoint. See `specs/2026-11-14-token-budget/`.
- **Claude provider (`AI_PROVIDER=anthropic`)**: `src/agent/anthropic.ts` implements an AI SDK v1 `LanguageModel` (`AnthropicChatModel`) on the official `@anthropic-ai/sdk` (beta Messages endpoint, key in `ANTHROPIC_API_KEY`), returned by `getFastModel`/`getCapableModel` in `provider.ts`, so every `generateText`/`generateObject` call site and the stored `CoreMessage` history work unchanged. It always uses **Claude Haiku 5.5** (`claude-haiku-5-5`) for both tiers; `AI_MODEL`/`AI_MODEL_FAST`/`AI_MODEL_CAPABLE` are ignored, so the CAPABLE synthesis request is skipped. `AI_REASONING_EFFORT` becomes `output_config.effort` (`low`–`max`; `minimal`/`none` map to `low`; unset = Haiku's default `medium`). The adapter enforces Haiku 5.5's request rules: sampling parameters are never sent; a trailing assistant turn gets a short user turn appended (prefill is a 400); system messages anywhere in the prompt are merged into `system`; forced `toolChoice` becomes `auto` plus a prompt instruction (a forced call skips thinking); `max_tokens` has a 4,096 floor because adaptive thinking spends it; orphaned tool calls/results and non-conforming tool ids from history stored under another provider are repaired. Tools run only on `stop_reason: tool_use` (never after a refusal or a cut-off reply); a `refusal` maps to finish reason `content-filter`. **Thinking replay**: the v1 prompt cannot carry thinking blocks, so each assistant turn with tool calls is kept in an in-memory LRU (`ThinkingReplayCache`, 500 entries) keyed by its `tool_use` ids with a fingerprint of model, `system`, the name-sorted tool set and every earlier message (thinking excluded); it is replayed verbatim only when the fingerprint matches and the turn is unchanged (an extra input field only if it equals the schema default) — in practice within one `generateText` tool loop — and left out otherwise, which keeps requests valid under the history-editing check; `thinking.block_binding.prefix_mismatch_behavior: "drop_block"` is the safety net. **Latency**: every request sets automatic prompt caching (`cache_control: ephemeral`), so later tool-loop steps read the prefix from cache; per-call options come through `experimental_providerMetadata.anthropic` (`effort`, `thinking: "off"` → `{type: "disabled"}`, which caps effort at `high`), used by the `tmdb.ts` recommendation lists (`discoverMedia`: 9.0 s → 3.4 s). `AI_MODEL_FALLBACKS` and `fetchWithRateLimitRetry` do not apply (the SDK retries 429/5xx itself, 3 times). Claude takes no audio, so voice notes need `TRANSCRIPTION_URL` or `GOOGLE_GENERATIVE_AI_API_KEY`. See `specs/2026-11-20-claude-provider/`.
- **Claude context (`4.48.0`)**: Three behaviours apply only when `isAnthropicProvider()` is true; for the other providers routing, the history budget and the prompt for a narrowed tool set are unchanged (the `UNSUPPORTED` rule above is the one shared change). (1) **History view**: `processUserMessage` calls `prepareHistoryForModel(history, CLAUDE_HISTORY_CHAR_BUDGET, { compactOlderTurns: false })` — whole turns, newest first, not compacted, ceiling 60,000 characters, latest and previous turn always kept; `AI_HISTORY_CHAR_BUDGET` and the "a third when routing did not narrow" rule do not apply. The 20-message `trimHistory` still runs first, so the view is about five tool turns. (2) **Session gap**: before the first write of a turn, a typed message whose conversation was last saved more than 12 hours ago (`isSessionExpired`, `SESSION_GAP_MS` in `src/agent/session.ts`; a row with no `updated_at` counts as expired) clears the stored history, so the model view, the router's context step and `confirmGuard` all start empty. The activity time is read before `trimHistory`, which can save the row. A button tap never resets: the callback handler in `src/bot/messages.ts` passes `{ fromButton: true }` as the fourth argument of `processUserMessage`. The startup catch-up call (no new message) never resets either. (3) **Usage log**: `AnthropicChatModel.doGenerate` logs one line per request (`formatUsageLog`): uncached input, cache-read, cache-write and output tokens, elapsed milliseconds and the stop reason; the `promptTokens` returned to the AI SDK is still the sum. See `specs/2026-11-24-claude-context/`.
- **Shared Skill Consumption**: `checkServiceHealthTool`, `getDiskSpaceTool` (`system-tools.ts`), and all six `download-tools.ts` tools source their data from the `media-tools` package (`src/services/media-tools-client.ts`) rather than calling `services/{radarr,sonarr,plex,qbittorrent,nzbget}.ts` directly. `media-tools` is the canonical implementation, shared with `skills-marketplace`'s `service-health`/`download-queue` skills; other Radarr/Sonarr/Plex tools (content search/add/remove) are unaffected and keep using the bot's own service wrappers.

## Proxy Gateway & Webhook Server
- The bot includes an embedded web server running independently via `Bun.serve` in `src/proxy.ts`.
- **Default Port**: `3001` (configurable via `PROXY_PORT`).
- **Dashboard API**:
    - `GET /api/dashboard/status`: Returns comprehensive health and LLM latency metrics.
    - `GET /api/dashboard/logs`: Serves recent 100 lines of `agentic-media-bot-restart.log`.
    - `GET /api/dashboard/events`: Aggregates the latest 15 media webhook events persisted in SQLite.
    - `GET /api/settings/notifications` & `POST /api/settings/notifications`: Exposes endpoints to load and persist boolean toggle states for specific media events.
- **Web Interface (SPA)**: Serves a pre-built React + Vite interface from `proxy-ui/dist/` for unmatched GET routes.
- **Webhook Subsystems**:
    - **Payload Handling**: Parses `multipart/form-data` from Plex and extracts JSON `payload`.
    - **Persistence & Write Ownership**: Exactly one process writes each event to `media_events`. When the relay reaches the bot, the **bot is the sole writer** — the proxy must not also write, because both processes share `data/bot_data.sqlite` and `saveMediaEvent` dedups on `(service, event_type, title)` within a 60-second window; a proxy-written row would make the bot's own `dbSave()` return `false`, and `eventQueue` skips the Telegram notification whenever `dbSave()` is `false`. The proxy writes **only** when the relay throws (bot offline) or `BRAIN_WEBHOOK_URL` is unset, so history survives an unreachable bot.
    - **Payload Parsing**: Webhook bodies are parsed by `parseWebhookEvent` in `src/services/webhookParser.ts`, a side-effect-free module (no DB, no file, no network) kept separate from `src/proxy.ts` so it is unit-testable — importing `proxy.ts` would exit the process or bind a port. It returns `null` on a malformed payload, which is logged but never blocks the relay.
    - **Image Support**: If a thumbnail is specified, the service fetches it via local `fetch` and uploads it to Telegram as an `InputFile` to resolve `localhost` reachability issues.
    - **Toggle Persistence**: Notification preference is stored in the `metadata` table as `notifications_enabled` (string "true" or "false"), with granular event configuration managed by `proxy.ts`.
    - **Conditional Relay**: The server only forwards webhook payloads to the main bot instance if `BRAIN_WEBHOOK_URL` is set, otherwise natively processing them.
    - **Loopback Resiliency**: Webhook relay uses `127.0.0.1` by default to avoid Nginx/Proxy conflicts on `localhost`.
    - **Relay 200 Patch**: If the relay to the bot throws, the proxy records the event locally and still returns `200 OK` (with a bypass warning), so external services perceive success. Only a thrown `fetch` error counts as relay failure — a non-2xx *response* means the bot answered and therefore owns the write.
    - **NZBGet Event Source**: NZBGet has no native webhook support; it only makes outbound HTTP calls from extension scripts. The `AgenticMediaBot` extension in `extensions/nzbget/` supplies this, registered as both a queue script (`NZB_ADDED` → `added`) and a post-processing script (`NZBPP_TOTALSTATUS=SUCCESS` → `success`). It targets the proxy by default, like Radarr/Sonarr/Plex. Requires NZBGet v23+ for the `manifest.json` extension format, and must be enabled in NZBGet's `Extensions` setting — installing the files is not sufficient. Install via `scripts/install-nzbget-extension.sh`.
    - **`mediaTools` Service Dispatch**: `proxy.ts` registers a `mediaTools` entry in its `services` dispatch map (alongside `radarr`/`sonarr`/`plex`/`qbittorrent`/`nzbget`/`tools`), backed by the `media-tools` package's `ServiceHealthManager`/`DownloadQueueManager` plus `src/services/ollamaClassifier.ts`. `media-tools` is an `optionalDependency` (`file:../../media-tools`) resolvable only on this local host — the remote bot never imports it directly, only via `executeOnProxy("mediaTools", …)`. Note: because the existing "Proxy Tool Interception" logic in `agent/index.ts` already RPCs *every* tool's `execute()` to the proxy's `tools` service when `USE_PROXY=true`, `checkServiceHealthTool`/`download-tools.ts`'s calls into `media-tools-client.ts` end up running on the proxy host itself — where `isProxyEnabled()` is false — so they resolve via `media-tools-client.ts`'s local-dev branch (direct import), not a second `mediaTools` RPC hop. The `mediaTools` dispatch entry is exercised directly only by Step 0's `classifyIntent` call, which runs in `agent/index.ts` before any tool-calling loop.

## Startup Verification & Specification Auditing
- On every run, the bot MUST execute `src/verify-config.ts` (or equivalent) to audit its environment against `TECHNICAL_SPEC.md` and `FUNCTIONAL_SPEC.md`.
- **Validation Rules**:
    1. Check for missing environment variables.
    2. Ensure service connectivity.
    3. Verify that the agent's current tool set matches the functionalities described in the FUNCTIONAL_SPEC.
    4. Detect and warn about multiple running instances of the bot script to prevent 409 Conflict errors.
    5. If significant spec changes are detected since the last run, notify administrators.
- Startup catch-up can be skipped once after admin-triggered restart via metadata flag.
- Changelog data in `src/bot.ts` is maintained as semantic-versioned release entries, and startup notifications send the latest release once per version upgrade.
- Admin startup changelog notifications are chunked below Telegram's 4096-character message limit before sending.
- **Per-admin delivery retry**: Failed admin IDs are stored in the `changelog_failed_admin_ids` metadata key. On every subsequent startup, still-pending admins are retried (even if the current version is already committed) until all deliveries succeed.
- **Verification Logic:**
    - On every run, the bot executing `src/verify-config.ts` (or equivalent) to audit its environment against `TECHNICAL_SPEC.md` and `FUNCTIONAL_SPEC.md`.
    - **Anthropic (Claude) Connectivity**: With `AI_PROVIDER=anthropic`, requires `ANTHROPIC_API_KEY`, and sends one short request to Claude Haiku 5.5. The Gemini check is skipped for this provider.
    - **Audio Transcription Provider check**: Reports which provider is active (`TRANSCRIPTION_URL`, Ollama, OpenAI, or Gemini) and warns if none is configured.
    - **Known gap**: `verify-config.ts`'s "OpenAI/OpenRouter Connectivity" check validates `OPENAI_API_KEY` when `AI_PROVIDER=openai`, but the agent's model selection (`agent/index.ts`) only branches on `ollama` vs. default Google — `openai` as an `AI_PROVIDER` value is not actually wired to chat responses today. Documented here rather than fixed; do not advertise `openai` as a supported `AI_PROVIDER` value in `.env.example` or `README` until this is resolved.
    - **Deployment:** The bot MUST be restarted after any functional or technical update to apply changes and trigger the startup audit/changelog notification.

## Onboarding & Configuration
- **Interactive Setup**: `src/setup.ts` utilizes the native `prompt` and `fetch` APIs to provide a guided configuration experience without external heavy CLI frameworks.
- **Dependency Check**: Uses `existsSync` to detect `node_modules` and `Bun.spawnSync` for automated `bun install` execution.
- **Plex API Integration**: Performs a real-time probe of the user's Plex server during setup to fetch and display library section IDs, reducing manual configuration errors.
- **Launch on Startup (Systemd)**: Creates a user-level systemd service unit (`~/.config/systemd/user/agentic-media-bot.service`) on Linux, configured to use the local `bun` binary and project directory.
- **Environment Persistence**: Atomically writes gathered configuration to `.env.local`.
- **Single-tenant model**: one running bot instance serves one arr stack, shared by every ID in `ALLOWED_USER_IDS`. There is no per-user credential storage or multi-stack routing.
